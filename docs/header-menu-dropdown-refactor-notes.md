# Header 菜单下拉重构公共注意事项

本文档记录在 `Drapery` 菜单下拉重构过程中遇到的实际问题。后续开发 `Shades`、`Hardware`、`Free Swatches`、`Sale` 时，优先先看这份文档。

## 1. 要注意先确认“路由是否真的命中特殊模板”

现象：

- 写了特殊菜单 snippet
- 但前台仍然显示默认 dropdown UI

原因：

- 一级菜单虽然已经接入 router
- 但 router 的标题匹配逻辑不一定真的命中特殊模板

经验：

- 不要默认认为 router 已经切换成功
- 每次开始一个新菜单时，先确认该一级菜单确实已经进入自己的专用 snippet
- 优先使用简单、直接、可控的标题字符串匹配

建议：

- 特殊菜单路由优先沿用当前已确认的“标题字符串匹配”方案
- 不要为了抽象而过早引入更复杂的匹配方式

## 2. 要注意特殊模板一旦接管后，先验证 dropdown 是否还能正常弹出

现象：

- `Drapery` 命中特殊模板后，一度出现 hover 后不弹出 dropdown

原因判断：

- 不一定是 JS hover 坏了
- 更可能是特殊模板本身输出异常，导致 dropdown 容器结构不完整或内容没有正常渲染

经验：

- 接入特殊模板后的第一步，不是先看 UI 对不对
- 而是先看 dropdown 有没有正常出现

建议：

- 每个新菜单开始开发时，先做最小版本模板
- 先确认 hover 后 dropdown 能正常出现
- 再逐步叠加右侧图片区、底部内容区、特殊排版

## 3. 要注意 Shopify Liquid 条件写法尽量保守

现象：

- `Drapery` 模板中使用带括号的复合条件后，出现 dropdown 不显示的问题

经验：

- Shopify Liquid 对复杂布尔表达式的兼容性不值得过度信任
- 尤其是带括号的复合判断，容易让排查变复杂

建议：

- 不要在模板里堆复杂判断
- 先在顶部用 `liquid` 代码块把布尔变量算出来
- 下面只用简单的布尔变量做 `if`

推荐写法：

- 先算 `has_xxx = true / false`
- 再写 `{% if has_xxx %}`

不推荐写法：

- 在模板输出区直接写长串复合判断

## 4. 要注意“菜单树数据”和“额外展示数据”要分开理解

在这次重构里，出现过一个典型混淆：

- 左侧二级、三级菜单来自 Shopify 后台菜单树
- 右侧图片、底部图文、额外 CTA 不来自菜单树

经验：

- 只要设计图里出现图片、文案、按钮、底部附加内容，这些通常都不应该强塞进菜单树逻辑里

建议：

- 菜单层级数据继续来自：
  - 一级菜单 `link`
  - 二级菜单 `link.links`
  - 三级菜单 `child_link.links`
- 额外 UI 内容继续来自：
  - Header section 的专用 block

## 5. 要注意专用 block 如果只服务一个菜单，就不要再加多余的匹配字段

现象：

- `Drapery menu promotion` 一开始设计了 `Link name`
- 但后来确认这套 block 只给 `Drapery` 用

问题：

- block 类型已经是专用的
- 再加一个 `Link name` 只会增加冗余和出错点

经验：

- 如果一个 block 类型天然只服务一个一级菜单，就不要再让它重复做“绑定一级菜单”的动作

建议：

- 专用菜单 block 直接按 `block.type` 读取
- 只有当“同一种 block 需要被多个一级菜单复用”时，才考虑加入匹配字段

## 6. 要注意先做最小可用版本，不要一开始就把所有设计细节一起压进去

`Drapery` 的实际开发过程证明：

- 一口气把路由、布局、图片区、底部图文、block 读取、样式全部同时压进去，问题会更难定位

建议顺序：

1. 先让特殊菜单成功命中特殊模板
2. 再确认 dropdown 正常弹出
3. 再渲染左侧基础二级、三级菜单
4. 再接右侧图片区
5. 再接底部附加内容
6. 最后再调样式细节

## 7. 要注意“没变化”和“完全不显示”是两类不同问题

这次实际遇到了两种不同现象：

1. `Drapery` hover 后还是默认 UI
2. `Drapery` hover 后不弹 dropdown

这两类问题的定位方向完全不同：

- “还是默认 UI”
  说明大概率是 router 没命中特殊模板

- “不弹 dropdown”
  说明大概率是特殊模板已经接管，但模板输出本身有问题

建议：

- 后续排查时，不要把这两类问题混在一起看
- 先确认是“没切过去”，还是“切过去后坏了”

## 8. 要注意每个特殊菜单都应该先有自己的设计说明文档和截图目录

`Drapery` 的这一步是有帮助的。

经验：

- 先有单独目录
- 先有设计说明文档
- 先有截图

这样在开发时更容易确认：

- 哪些部分来自菜单树
- 哪些部分来自 block 配置
- 哪些部分只是视觉样式

建议目录结构延续当前做法：

- `docs/<menu>-menu-refactor/`
- `<menu>-design.md`
- `screenshots/`

## 9. 要注意每开发完一个特殊菜单，都要同步更新总任务文档

经验：

- 如果不及时更新阶段状态，后面很容易忘记当前是“需求确认已完成”还是“代码已完成待验收”

建议：

- 每完成一个菜单的一个关键节点，就同步更新：
  - [docs/header-menu-dropdown-refactor-plan.md](/mnt/d/dbc%20projects/cozyology-com-symmetry_7-21_install-gtm-kit/docs/header-menu-dropdown-refactor-plan.md)

建议至少更新这些状态：

- 需求确认已完成
- 代码已实现
- Shopify 后台已验收
- 是否还有遗留问题

## 10. 要注意每个特殊菜单都先判断是否真的需要“公共抽离”

这次 `Drapery` 的经验说明：

- 在第一个特殊菜单阶段，优先把它独立跑通更重要
- 不要过早把注意力放在“是否立刻抽公共组件”

建议：

- 在 `Drapery`、`Shades`、`Hardware` 做出 2 到 3 个之后
- 再回头看哪些结构已经明显重复
- 那时再做公共抽离，判断会更准确

## 11. 要注意先写“能稳定工作的结构”，再追求完全贴图

经验：

- 第一个特殊菜单的目标，应该先是“结构正确、数据来源清晰、可继续迭代”
- 而不是第一次就把所有视觉细节一次性打磨到最终状态

建议：

- 每个特殊菜单第一轮开发目标优先级：
  1. 路由正确
  2. 结构正确
  3. 数据可配置
  4. 视觉接近设计图
  5. 细节微调
